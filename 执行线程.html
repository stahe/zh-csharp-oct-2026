    8. 执行线程

    本章介绍在单个程序中同时执行多段代码：线程 （执行线程）以及用于同步它们的工具。在 2008 年，大多数机器只有一个处理器，并行在很大程度上是由操作系统营造的假象。如今，即使最普通的笔记本电脑 也有多个核心：多个线程确实在同时运行，这使这里讨论的同步问题更加普遍。

    示例是位于 [dotnet run threads-01.cs] 文件夹中的单文件应用程序（[08-threads]）。请注意，这些应用程序的隐式 [using] 指令包括 [System.Threading] 和 [System.Threading.Tasks]：类 [Thread]、[Lock]、[Mutex]、[Monitor]、[Interlocked]、[Task]……无需 [using] 指令即可使用。

    开始之前先提醒一句：多线程程序的结果每次执行都可能不同。线程获得处理器的顺序取决于操作系统、处理器数量以及机器的负载。本章所示的结果是在一台与其他程序共享的双处理器 Linux 机器上得到的。如果你运行这些示例，会得到相似的结果，但很少会完全相同。

    8.1. Thread 类

    应用程序启动时，它在一个称为线程的执行流中运行。在 .NET 中对线程建模的类是 [System.Threading.Thread] 类。它的主要构造函数、属性和方法如下：

    8.2. 创建执行线程

    应用程序中可以有一些代码段在不同的执行线程中“同时”执行。如果机器的处理器数量少于准备执行的线程数，这些线程就共享处理器：每个线程轮流使用处理器很短的时间（几毫秒）。在多处理器机器上，多个线程确实同时执行。分配给线程的时间取决于多种因素，包括它的优先级，该优先级有默认值，但也可以通过编程设置（属性 [Priority]）。获得处理器的线程可以提前释放它：

    • 通过等待某个事件（使用 [Join] 等待另一个线程结束、等待信号）；
    • 通过进入休眠状态一段指定的时间（[Sleep]）。

    线程 T 首先使用上面介绍的某个构造函数创建，例如：

    1
    Thread t = new Thread(Display);

    其中 [Display] 是具有以下两种签名之一的方法：

    1
2
    void Display();
void Display(object? obj);

    创建线程并不会启动它：

    • 线程 T 的执行由 [T.Start()] 启动：传给 T 的构造函数的方法随后由线程 T 执行。执行指令 [T.Start()] 的代码不会等待线程 T 结束；它会立即转到下一条指令。这样我们就有两个线程在并行运行。它们常常需要相互通信，以跟踪共同工作的进度：这就是线程 同步问题；
    • 线程 T 一旦启动，就自主运行。当它所执行的方法完成时，它就停止；
    • 我们可以使用 [T.Join()] 等待它执行完毕。这是一条阻塞指令：执行它的线程会被阻塞，直到线程 T 完成其工作。这是一种基本的同步方法。

    // 创建执行线程

// 我们给主线程命名
Thread.CurrentThread.Name = "Main";

// 创建 5 个线程
var tasks = new Thread[5];
for (int i = 0; i < tasks.Length; i++)
{
    // 第 i 号线程将执行 Display 方法
    tasks[i] = new Thread(Display);
    // 我们给它命名
    tasks[i].Name = i.ToString();
    // 我们启动它的执行（非阻塞操作）
    tasks[i].Start();
}

// 主线程结束
Console.WriteLine($"End of thread {Thread.CurrentThread.Name} at {DateTime.Now:HH:mm:ss.fff}");

// 由各线程执行的方法
static void Display()
{
    // 执行该方法的线程
    Thread current = Thread.CurrentThread;
    Console.WriteLine($"Start of execution of the Display method in thread {current.Name} (id {current.ManagedThreadId}): {DateTime.Now:HH:mm:ss.fff}");
    // 休眠 1 秒
    Thread.Sleep(1000);
    Console.WriteLine($"End of execution of the Display method in thread {current.Name}: {DateTime.Now:HH:mm:ss.fff}");
}

    说明：

    • 第 4 行：我们给主线程命名；
    • 第 7–15 行：创建并启动 5 个线程。它们的引用存储在数组中，以便以后获取。每个线程执行第 22–29 行的 [Display] 方法；
    • 第 11 行：方法名 [Display] 被自动转换为 [ThreadStart] 类型的委托（委托在上一章中介绍过）；
    • 第 15 行：启动第 i 号线程。该操作是非阻塞的：第 i 号线程与启动它的主线程并行运行；
    • 第 19 行：主线程到达程序末尾；
    • 第 22–29 行：方法 [Display] 显示执行它的线程的名称和 ID，以及执行的开始和结束时间（精确到毫秒）；
    • 第 28 行：任何执行 [Display] 方法的线程都会暂停 1 秒。处理器随后交给另一个等待处理器的线程。1 秒的暂停结束时，被暂停的线程重新具备获得处理器的资格。轮到它时它就会得到处理器。

    // 使用 Join 等待线程结束 - 用 lambda 创建的线程

// 我们给主线程命名
Thread.CurrentThread.Name = "Main";

// 创建 5 个线程
var tasks = new Thread[5];
for (int i = 0; i < tasks.Length; i++)
{
    // i 的本地副本，被 lambda 捕获
    int number = i;
    // 线程执行 lambda，lambda 以带类型的参数调用 Display
    tasks[i] = new Thread(() => Display(number, 1000 + 100 * number)) { Name = i.ToString() };
    tasks[i].Start();
}

// 我们等待所有线程结束
foreach (Thread task in tasks)
{
    // 主线程被阻塞，直到线程 [task] 结束
    task.Join();
}
// 主线程结束
Console.WriteLine($"End of thread {Thread.CurrentThread.Name} at {DateTime.Now:HH:mm:ss.fff}");

// 由各线程执行的方法
static void Display(int number, int duration)
{
    Console.WriteLine($"Start of execution of task {number} in thread {Thread.CurrentThread.Name}: {DateTime.Now:HH:mm:ss.fff}");
    // 休眠 [duration] 毫秒
    Thread.Sleep(duration);
    Console.WriteLine($"End of execution of task {number} in thread {Thread.CurrentThread.Name}: {DateTime.Now:HH:mm:ss.fff}");
}

    说明：

    • 第 13 行：线程执行 Lambda [() => Display(number, 1000 + 100 * number)]。无参数、无返回值的 Lambda 与委托 [ThreadStart] 兼容。这种语法允许你调用带有类型化参数的方法（这里是两个 [int]），而不必采用规定的签名 [void M(object? obj)]；
    • 第 11 行：Lambda 使用的是循环变量 [i] 的副本。这是必不可少的：Lambda 捕获的是变量，而不是它的值。在 [for] 循环中，变量 [i] 在所有迭代中是唯一的；如果 Lambda 使用 [i]，较晚启动的线程可能读到后续迭代中 [i] 的值，甚至读到最终值 5。相反，在循环体内声明的变量 [number] 在每次迭代中都是一个新变量（自 C# 5 起，[foreach] 循环变量在每次迭代中也是新的）；
    • 第 18–21 行：主线程等待每一个线程。它先被阻塞以等待线程 0，然后等待线程 1，依此类推。当它退出循环时，它启动的 5 个线程都已结束；
    • 第 31 行：任务 #i 休眠 1,000 + 100 × i 毫秒，使线程按已知的顺序结束。

    8.3. 线程的好处

    现在我们已经强调了默认线程（执行主程序的线程）的存在，并且知道如何创建其他线程，接下来我们来看看线程的好处。它们主要有两种用途：

    • 为了在耗时的计算中利用 机器上所有的 处理器 ：将工作分成若干块，分配给不同的线程。我们将在本章末尾使用 [Parallel] 库来做到这一点；
    • 为了同时执行多个任务，尤其是当其中一些任务主要涉及等待（等待网络响应、磁盘读取或用户输入）时。客户端/服务器式的互联网应用程序就是这种情况，我们将在后面的章节中讨论。

    在客户端/服务器式的互联网应用程序中，位于名为 S1 的机器上的服务器响应位于远程机器 C1、C2、……、Cn 上的客户端的请求：

    8.5.1. 不同步的并发访问

    在前面的段落中，信息只在两个线程之间、并且在非常明确的时刻交换：这是参数传递的经典例子。还有一些情况下，信息由多个线程共享，它们可能想同时读取或更新这些信息。这就引出了这些信息的完整性问题。假设共享的信息是一个结构 S，包含各种信息 I1、I2、……、In：

    • 线程 T1 开始更新结构 S：它修改了字段 I1，并在完成对结构 S 的完整更新之前被中断；
    • 获得处理器的线程 T2 随后读取结构 S 以作出决策。它读取到的是处于不稳定状态的结构：有些字段是最新的，有些则不是。

    • 临界资源 是一次只能被一个线程持有的资源。这里，临界资源就是计数器；
    • 程序的临界区 是线程执行流中访问临界资源的一段指令序列。我们必须确保，在这个临界区内，该线程是唯一能访问该资源的线程。

    8.5.3. Mutex 类

    [System.Threading.Mutex] 类同样可以界定临界区。它与 [lock] 子句在可见范围上有所不同：

    • [lock] 子句在同一应用程序内同步线程；
    • 如果给定名称，[Mutex] 类可以同步来自不同应用程序（或进程）的线程。

    [Mutex] 是操作系统对象：使用它比使用 [lock] 消耗的资源多得多。因此，对于同一进程内的线程，我们更倾向于使用 [lock]；[Mutex] 主要用于进程之间。我们将使用以下构造函数和方法：

    作用
    [Mutex()]

    1

    8.5.6. Interlocked 类

    [Interlocked] 类使对变量的简单操作成为 原子操作：该操作由线程完整执行，其他线程不可能在操作中途观察或修改该变量。前面的工具（[lock]、[Mutex]、[AutoResetEvent]）都是用来使一组操作成为原子操作的，代价是阻塞其他线程。对于简单但频繁的操作，[Interlocked] 类通过使用特殊的处理器指令来避免这种阻塞。它的主要静态方法如下：

    方法
    作用
    [int Increment(ref int x)]
    将 [x] 加 1 并返回新值
    [int Decrement(ref int x)]
    将 [x] 减 1 并返回新值
    [int Add(ref int x, int value)]
    将 [value] 加到 [x] 上并返回新值
    [int Exchange(ref int x, int value)]
    将 [value] 赋给 [x] 并返回旧值
    [int CompareExchange(ref int x, int value, int comparand)]
    仅当 [x] 等于 [comparand] 时，才将 [value] 赋给 [x]；返回 [x] 的先前值
    [long Read(ref long x)]

    这些方法适用于类型 [int]、[long]、[uint]、[ulong]，而 [Exchange] 和 [CompareExchange]还适用于其他类型。方法 [And] 和 [Or] （.NET 5）以原子方式执行按位“与”或“或”运算。参数按引用传递（[ref]）：[Interlocked] 必须作用于变量本身，而不是副本。因此，该变量必须是字段或局部变量；属性不能按引用传递。

    8.6. 对多个共享资源的并发访问

    8.6.1. 死锁

    在前面的示例中，各个线程共享的是单个资源。如果有多个资源且它们相互依赖，情况就会更复杂。特别是可能发生死锁：两个线程相互等待。考虑下面依次发生的操作：

    • 线程 T1 获取锁 V1 以访问共享资源 R1；
    • 线程 T2 获取锁 V2 以访问共享资源 R2；
    • 线程 T1 请求锁 V2。它被阻塞；
    • 线程 T2 请求锁 V1。它被阻塞。

    线程 T1 和 T2 无限期地相互等待。有几种可行的解决方案：

    • 使用单个锁同时请求两个资源。如果这会导致长时间锁定一个代价高昂的资源，这种做法并不总是可行；
    • 始终 按相同的顺序获取锁：如果所有线程都先获取 V1 再获取 V2，就不可能发生死锁。这是最常用的规则；
    • 持有 V1 但无法获取 V2 的线程释放 V1，以避免死锁。

// 获取第一个资源，然后在 [timeout] 内尝试获取第二个
static void Work(Lock first, string firstName, Lock second, string secondName, TimeSpan timeout)
{
    string name = Thread.CurrentThread.Name ?? "?";
    lock (first)
    {
        Console.WriteLine($"{DateTime.Now:HH:mm:ss.fff}: {name} obtained {firstName}");
        // 我们给另一个线程留出时间获取它的第一个资源
        Thread.Sleep(500);
        Console.WriteLine($"{DateTime.Now:HH:mm:ss.fff}: {name} requests {secondName}");
        // 带最长等待时间的请求，而不是无限期等待的锁
        if (second.TryEnter(timeout))
        {
            try
            {
                Console.WriteLine($"{DateTime.Now:HH:mm:ss.fff}: {name} obtained {secondName} and works with {firstName} and {secondName}");
            }
            finally
            {
                second.Exit();
            }
        }
        else
        {
            Console.WriteLine($"{DateTime.Now:HH:mm:ss.fff}: {name} did not obtain {secondName} within {timeout.TotalSeconds} s: it releases {firstName} and gives up");
        }
    }
}

    说明：

    • 第 4–5 行：两个资源的锁。这里它们是局部变量，被第 8–10 行的 Lambda 捕获；
    • 第 8 行：线程 T1 获取 R1，然后请求 R2；它最多等待 2 秒；
    • 第 10 行：线程 T2 获取 R2，然后请求 R1——也就是说顺序相反；它最多等待 5 秒；
    • 第 21 行：线程获取它的第一个资源；
    • 第 25 行：它等待半秒钟，这让另一个线程有时间获取它自己的第一个资源：于是死锁必然发生；
    • 第 28 行：线程不使用会无限期等待的 [lock] ，而是带最长等待时间请求第二把锁。[TryEnter] 在获取到锁时返回 [true] ，超时则返回 [false]；
    • 第 36 行：通过 [TryEnter] 获取的锁必须在 [finally] 子句中通过 [Exit] 释放；
    • 第 39–41 行：如果无法获取第二把锁，线程就中止。退出 [lock] 块时，它会释放自己的第一个资源。

    8.6.2. 示例：读者与写者

    考虑下面的示例：

    • 我们有一个数组，一些线程向其中写入数据（写者），另一些线程读取数据（读者）；
    • 写者彼此平等但互斥：同一时刻只有一个写者可以向数组存入数据；
    • 读者彼此平等但互斥：同一时刻只有一个读者可以读取数组中存储的数据；
    • 只有在写者放入数据之后，读者才能从数组中读取数据；只有在数组中已有的数据被读者读取之后，写者才能向数组放入新数据。

    共享资源有两种类型：

    • 被写入的数组：同一时刻只有一个写者可以访问它；
    • 被读取的数组：同一时刻只有一个读者可以访问它。

    并且这些资源的使用有先后顺序：

    • 读者必须始终跟在写者之后；
    • 写者必须始终跟在读者之后，第一次除外。

    对这两个资源的访问可以使用两个 [AutoResetEvent] 类型的屏障来控制：

    • [canWrite] 屏障控制写者对数组的访问；
    • 屏障 [canRead] 控制读者对数组的访问；
    • [canWrite] 屏障以打开状态创建，允许第一个写者通过并阻塞所有其他写者；
    • [canRead] 屏障创建时处于关闭状态，阻塞所有读取者；
    • 写入者完成工作后，会打开屏障 [canRead] 以放行一个读取者；
    • 读取者完成工作后，会打开屏障 [canWrite] 以放行一个写入者。

static class Board
{

    private static readonly int[] data = new int[3];
    // 表示可以读取 data 的内容：起初为关闭状态
    private static readonly AutoResetEvent canRead = new(false);
    // 表示可以写入 data：起初为打开状态
    private static readonly AutoResetEvent canWrite = new(true);

    // 读取数组的内容
    public static void Read()
    {
        string name = Thread.CurrentThread.Name ?? "?";
        Console.WriteLine($"Method [Read] started by thread {name}");
        // 我们等待读取许可
        canRead.WaitOne();
        // 读取数组
        for (int i = 0; i < data.Length; i++)
        {
            // 等待 0.5 秒：线程让出处理器
            Thread.Sleep(500);
            Console.WriteLine($"{DateTime.Now:HH:mm:ss.fff}: reader {name} read the number {data[i]}");
        }
        // 我们允许一个写者
        canWrite.Set();
        Console.WriteLine($"Method [Read] finished by thread {name}");
    }

    // 写入数组
    public static void Write()
    {
        string name = Thread.CurrentThread.Name ?? "?";
        Console.WriteLine($"Method [Write] started by thread {name}");
        // 我们等待写入许可
        canWrite.WaitOne();
        // 写入数组
        for (int i = 0; i < data.Length; i++)
        {
            // 等待 0.5 秒
            Thread.Sleep(500);
            // Random.Shared 可以被多个线程使用
            data[i] = Random.Shared.Next(0, 1000);
            Console.WriteLine($"{DateTime.Now:HH:mm:ss.fff}: writer {name} wrote the number {data[i]}");
        }
        // 我们允许一个读者
        canRead.Set();
        Console.WriteLine($"Method [Write] finished by thread {name}");
    }
}

    • 只有数组中有内容可读时，读取者才会读取；
    • 只有数组被完全读完后，写入者才会写入；
    • 不过，执行顺序是无法控制的：没有任何理由规定写入者 W0 必须先于写入者 W1，也没有理由规定读取者 R0 必须先于读取者 R1。再次执行时，顺序可能不同。

    8.6.3. Monitor 类

    在前面的示例中，当写入者在指令 [canWrite.WaitOne()] 处被阻塞时，其中一个（任意一个）会被操作 [canWrite.Set()] 解除阻塞。如果想为某个特定的写入者打开屏障，事情就变得复杂了。

    以设有服务窗口的公共服务办事处为例。顾客到达时，从取号机上取一张编号的号码票，然后去坐下。顾客的号码会通过扩音器被叫到。等待期间，顾客可以做任何想做的事：看书或打盹。每次扩音器报出一个号码，他们就会被唤醒。如果是自己的号码，顾客就起身走向窗口；否则就回去继续做刚才的事。我们可以用类似的方式来操作线程。以写入者为例：

    在办事窗口

    几位写入者在等待同一个窗口
    它们的线程被阻塞
    窗口空闲，下一位写入者的号码被叫到
    刚才读取数组的线程通知写入者数组已可用。由该线程或另一个线程来决定应该由哪个写入者继续
    每位写入者核对自己的号码；只有号码被叫到的那一位前往窗口，其他人回到等待队列
    每个线程检查自己是否被选中。如果是，就通过屏障；否则回到等待队列

// 共享资源及其同步
static class Board
{
    // 读者和写者之间共享的数组
    private static readonly int[] data = new int[3];
    // 读计数器和写计数器的访问令牌
    private static readonly object canRead = new();
    private static readonly object canWrite = new();
    // 计数器的访问条件
    private static bool readingAllowed = false;
    private static bool writingAllowed = false;
    private static int nextReader = 0;
    private static int nextWriter = 0;
    // 读者和写者的顺序
    public static string[] ReadOrder { get; set; } = [];
    public static string[] WriteOrder { get; set; } = [];

    // 打开写计数器
    public static void AllowWriting()
    {
        lock (canWrite)
        {
            writingAllowed = true;
            // 我们唤醒所有等待令牌的写者
            Monitor.PulseAll(canWrite);
        }
    }

    // 读取数组的内容
    public static void Read()
    {
        string name = Thread.CurrentThread.Name ?? "?";
        Console.WriteLine($"Method [Read] started by thread {name}");
        // 我们请求读计数器的令牌
        lock (canRead)
        {
            // 只要还没轮到我们，就归还令牌并等待
            while (!readingAllowed || ReadOrder[nextReader] != name)
            {
                Monitor.Wait(canRead);
            }
            // 在计数器处：读取数组
            for (int i = 0; i < data.Length; i++)
            {
                Thread.Sleep(500);
                Console.WriteLine($"{DateTime.Now:HH:mm:ss.fff}: reader {name} read the number {data[i]}");
            }
            // 下一个读者
            readingAllowed = false;
            nextReader++;
            // 我们通知写者可以写入了
            lock (canWrite)
            {
                writingAllowed = true;
                Monitor.PulseAll(canWrite);
            }
            Console.WriteLine($"Method [Read] finished by thread {name}");
        }
    }

    // 写入数组
    public static void Write()
    {
        string name = Thread.CurrentThread.Name ?? "?";
        Console.WriteLine($"Method [Write] started by thread {name}");
        // 我们请求写计数器的令牌
        lock (canWrite)
        {
            // 只要还没轮到我们，就归还令牌并等待
            while (!writingAllowed || WriteOrder[nextWriter] != name)
            {
                Monitor.Wait(canWrite);
            }
            // 在计数器处：写入数组
            for (int i = 0; i < data.Length; i++)
            {
                Thread.Sleep(500);
                data[i] = Random.Shared.Next(0, 1000);
                Console.WriteLine($"{DateTime.Now:HH:mm:ss.fff}: writer {name} wrote the number {data[i]}");
            }
            // 下一个写者
            writingAllowed = false;
            nextWriter++;
            // 我们通知读者可以读取了
            lock (canRead)
            {
                readingAllowed = true;
                Monitor.PulseAll(canRead);
            }
            Console.WriteLine($"Method [Write] finished by thread {name}");
        }
    }
}

    对读取窗口的访问受以下元素约束：

    • 第 36 行：令牌 [canRead]；
    • 第 39 行：布尔值 [readingAllowed]；
    • 第 44 行：已排序的读取者名称数组。读取者按该数组规定的顺序前往读取窗口；
    • 第 41 行：[nextReader] 是该数组中下一个被授权前往窗口的读取者的索引。

    对写入窗口的访问同样由令牌 [canWrite]、布尔值 [writingAllowed]、数组 [WriteOrder] 和索引 [nextWriter] 控制。

    主程序：

    • 第 7–9 行：读取者按创建顺序的逆序（R2、R1、R0）前往窗口，写入者按创建顺序（W0、W1、W2）前往窗口。这些数组通过集合表达式 [.. sequence] 构建，它从 LINQ 查询创建数组；
    • 第 18–22 行：创建并初始化读取者，然后是写入者。它们都会被阻塞，因为此时既不允许读取也不允许写入；
    • 第 26 行：允许写入，并通知写入者有变化发生（方法 [AllowWriting]，第 48–54 行）。

    [Read] 方法：

    • 第 64–86 行：读取窗口的整个过程由 [lock] 对令牌 [canRead] 的加锁控制。获得该令牌的读取者在整个窗口停留期间都持有它；
    • 第 67–69 行：已取得令牌的读取者，如果不允许读取或者还没轮到它，就归还令牌；
    • 第 72–75 行：通过窗口（读取数组）；
    • 第 78–79 行：读取者修改读取窗口的访问条件。它仍然持有读取令牌，这些修改会阻止其他任何读取者访问窗口；
    • 第 81–84 行：读取者修改写入窗口的访问条件，并通知所有等待中的写入者有变化发生。为此，它获取令牌 [canWrite]：由此可见，该线程同时持有两个令牌。写入者以相反的顺序做同样的事（它们持有 [canWrite] 并请求 [canRead]），这就是前面描述的死锁情形。不过这里没有风险：线程只在结束窗口访问时才请求第二个令牌；两个窗口永远不会同时被占用；其他线程持有令牌的时间仅够检查访问条件，并不会请求另一个令牌。

    前面的示例保护的是非常简单的共享数据（一个计数器、一个数组）。当线程共享集合（列表、字典、队列）时，可以用 [lock] 保护每一次访问。但是普通集合（[List<T>]、[Dictionary<TKey,TValue>]、[Queue<T>]）并不是为被多个线程同时修改而设计的：不加保护地使用可能导致元素丢失、触发意料之外的异常，甚至破坏集合的内部结构。从 .NET 4 开始，[System.Collections.Concurrent] 命名空间提供了无需显式加锁即可在线程之间共享的集合：

    [ConcurrentStack<T>]

    8.8. 线程池

    到目前为止，要管理线程，我们都是用 [new Thread(...)] 创建它们，然后用 [Start()] 执行。创建线程是相对昂贵的操作：特别是系统必须为它分配一个栈，而且每个线程在存在期间都会占用内存。我们将在数据库一章中看到，存在连接池：已打开的连接被保留备用，并借给请求它们的线程，因为打开连接的开销很大。线程也有类似的机制：.NET 的 线程池 （ThreadPool）。

    • 只要池中的线程数低于最小阈值，池就会为每个找不到空闲线程的任务立即创建一个新线程。默认情况下，这个最小值是处理器数量；可以用 [ThreadPool.GetMinThreads(out min1, out min2)] 读取它，并用 [ThreadPool.SetMinThreads(min1, min2)] 修改它。线程池管理两类线程：执行分配给它们的作业的工作线程（min1），以及异步 I/O 线程（min2）；
    • 如果这个数量不够，线程池会逐步创建额外的线程，直到达到一个最大值，该最大值可以用 [ThreadPool.GetMaxThreads(out max1, out max2)] 读取，并用 [ThreadPool.SetMaxThreads(max1, max2)] 修改。达到最大值后，分配给线程池的作业会进入队列，直到有线程可用；
    • 完成了任务的线程不会被销毁：它会被归还到线程池，并用于下一个任务。

    线程池有两个优点：它节省了创建线程所花费的时间（少数几个线程就能处理数百个请求），并且通过限制线程数量，防止应用程序被过多的请求压垮。

    要把任务分配给线程池，请使用 [ThreadPool.QueueUserWorkItem(WaitCallback callback, object? state)] 方法，其中 [WaitCallback] 是签名为 [void M(object? state)] 的委托。该任务将由线程池中的一个线程执行，参数为 [state]。程序 [threads-20.cs] 如下：

{

    });

    8.10. 线程本地数据

    8.10.1. 原理

    考虑一个三层应用程序：

    假设该应用程序是多用户的，例如一个 Web 应用程序。每个用户请求由一个线程处理。该线程的生命周期如下：

    • 创建线程，或从线程池中获取线程，以满足用户的请求；
    • 如果该请求需要数据，线程就执行 [ui] 层中的一个方法，该方法调用 [business] 层中的一个方法，后者又调用 [dao] 层中的一个方法；
    • 线程把响应返回给用户。然后它要么终止，要么被归还到线程池。

    在第二步中，让线程拥有自己的数据可能很有用，也就是不与其他线程共享的数据。例如，这些数据可以属于该线程正在服务的特定用户，并在各个 [ui, business, dao] 层中使用，而无需作为参数传递给每个方法。

    2008 年的课程为此使用了方法 [Thread.SetData] 和 [Thread.GetData] ，它们为线程管理一种私有的字典。它们仍然存在，但很少使用；人们更倾向于使用两种更简单、更高效的工具：

    • 应用于静态字段的 [[ThreadStatic]] 特性：每个线程都有该字段自己的实例；
    • [ThreadLocal<T>] 类：这个对象的 [Value] 属性对每个线程有不同的值。传给构造函数的函数为每个线程提供初始值。

class Transaction
{
    private static int counter;
    private readonly Stack<Action> undos = new();
    public int Number { get; } = Interlocked.Increment(ref counter);

    // 记录撤销某次更新的操作
    public void Log(Action undo) => undos.Push(undo);
    // 提交事务：更新被保留
    public void Commit() => undos.Clear();
    // 回滚事务：更新被撤销，从最后一个到第一个
    public void Rollback()
    {
        while (undos.TryPop(out Action? undo))
        {
            undo();
        }
    }
}

    8.10.3. 结论

    前面的示例展示了线程本地数据在事务管理中的价值。但不应原样照搬它。.NET 通过 [System.Transactions.TransactionScope] 类开箱即用地提供了这一机制：一个“环境”事务，可通过 [Transaction.Current] 访问，数据库连接会自动参与其中。Entity Framework Core 等框架同样能管理事务，而无需 [dao] 层的代码去处理它们。而在如今异步的 Web 应用程序中，这种上下文信息是由 [AsyncLocal<T>] 而不是线程本地数据来承载的。
