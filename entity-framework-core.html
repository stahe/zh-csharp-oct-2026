    11. Entity Framework Core

    上一章展示了 .NET 应用程序如何通过 ADO.NET 连接器与数据库通信：打开连接，编写 SQL 命令，逐列读取结果行，并将它们复制到对象中。这种复制过程——从行到对象，以及从对象到 [INSERT]、[UPDATE] 和 [DELETE] 命令——是重复性的。可以借助工具将其自动化：ORM （对象关系映射器）。本章介绍 Microsoft 的 Entity Framework Core （EF Core）。

    2008 年的课程没有提到 ORM：它只是在数据库一章的结尾提到了“第三方数据访问框架”（NHibernate、iBatis）和 LINQ。Entity Framework 在几个月后发布（2008 年，随 .NET 3.5 SP1），2012 年作者为它专门编写了一门课程，题为“通过示例介绍 Entity Framework 5 Code First”。本章是全新的内容。它以第 10 章中的商品示例数据库为基础，最后给出税额计算应用程序的第 7 版，其 [dao] 层使用 EF Core。

    11.1. 什么是 ORM？

    11.1.1. 对象与表

    C# 应用程序处理的是 对象：商品有名称、价格和库存量；订单有客户和订单行列表，每个订单行都引用一件商品。关系数据库则将同样的信息存储在 表 中：每件商品对应 [articles] 表中的一行，每个订单对应 [orders] 表中的一行，行与行之间的关系由外键表示。这两个世界并不完全吻合：

    • 对象直接引用其他对象（[order.Client]）；行则包含另一行的主键值（[ClientId]）；
    • 对象可以包含集合（[order.Lines]）；表只包含单个值；集合由另一个表中指向该订单的行来表示；
    • C# 类型（[string]、[decimal]、[DateOnly]、[bool]）与 SQL 类型（[varchar(30)]、[decimal(10,2)]、[date]、[tinyint(1)]）并不相同；
    • 对象用 C#（以及 LINQ）查询，而表用 SQL 查询。

    ORM 在这两个世界之间架起桥梁。我们一劳永逸地定义类与表之间的映射（模型），之后由它负责：

    • 将用 C# 编写的 LINQ 查询翻译成 SQL 和 [SELECT] 命令；
    • 根据读取的行创建对象（这称为 实例化）；
    • 保存读取到的对象，并检测其中被修改、添加或删除的对象；
    • 生成 [INSERT]、[UPDATE]、和 [DELETE] 命令，将这些更改反映到数据库中；
    • 并在必要时，根据类创建和更新数据库架构（表、列、索引）。

    使用 EF Core 和 MySQL 的应用程序的架构如下：

    • [1]：应用程序。它的 [dao] 层不再与 ADO.NET 连接器通信，而是通过 [DbContext] 对象和 LINQ 查询与 EF Core 通信；
    • [2]：EF Core，与 DBMS 无关：模型、LINQ 查询的翻译、变更跟踪、迁移；
    • [3]：特定于 DBMS 的 EF Core 提供程序 （此处是用于 MySQL 的 Pomelo）：它了解该 DBMS 的 SQL 方言及其列类型；
    • [4]：该 DBMS 的 ADO.NET 连接器，即第 10 章中的那个（MySqlConnector）：EF Core 并不取代 ADO.NET，而是使用它；
    • [5]：DBMS。

    11.1.2. EF Core 与 Entity Framework 6

    有两个名为 Entity Framework 的产品：

    • Entity Framework 6 （EF 6），最初的产品，为 Windows 上的 .NET Framework 设计（自 6.3 版起，它也可在 .NET Core 及其后续版本上运行）。它仍在维护，但不再积极开发；
    • Entity Framework Core，一次完全重写的版本，于 2016 年随 .NET Core 发布。它可在所有 .NET 平台（Windows、Linux、macOS）上运行，所有新功能都在这个版本中提供。它的版本号与 .NET 保持一致：EF Core 8 对应 .NET 8，EF Core 9 对应 .NET 9，EF Core 10 对应 .NET 10。

    对于新应用程序，我们使用 EF Core。这两个产品的 API 相似（[DbContext]、[DbSet<T>]、LINQ、迁移），因此这里所述内容在很大程度上对 EF 6 同样适用。

    11.1.3. 提供程序

    EF Core 通过提供程序访问 DBMS，提供程序以 NuGet 包的形式分发。Microsoft 提供了 SQL Server、SQLite 和 Azure Cosmos DB 的提供程序；其他的由 DBMS 厂商或社区编写：用于 PostgreSQL 的 [Npgsql.EntityFrameworkCore.PostgreSQL] ，用于 Oracle 的 [Oracle.EntityFrameworkCore] ，用于 MySQL 的 [Pomelo.EntityFrameworkCore.MySql] 和 [MySql.EntityFrameworkCore] （来自 Oracle）。我们使用 Pomelo，这是使用最广泛的 MySQL 提供程序，它基于第 10 章中的 [MySqlConnector] 连接器。

    提供程序是针对特定版本的 EF Core 编译的：Pomelo 9 适用于 EF Core 9，而 Pomelo 的版本通常比 EF Core 晚发布几个月。本课程使用 EF Core 9.0.0 和 Pomelo 9.0.0，运行在 .NET 10 上。这种组合是可行的：EF Core 9 面向 .NET 8（[net8.0]），而为 .NET 8 编译的库 无需修改即可在 .NET 10 上运行。升级到 EF Core 10 只需修改包的版本号；除了生成的 SQL 中的一些细枝末节外，本章的代码应当无需修改即可运行。不过，在 LINQ 一节中，我们会遇到 EF Core 9 与 C# 14 编译器之间的一个小的不兼容问题。

    11.1.4. Code First 与 Database First

    EF Core 模型（类与表之间的映射）可以通过两种方式构建：

    • Code First：编写 C# 类，由 EF Core 据此推导出数据库架构，它可以自行创建数据库，并随着应用程序的演进对其进行更新（迁移）。这是本章以及作者 2012 年的课程所采用的方法；
    • Database First：数据库已经存在，使用 [dotnet ef dbcontext scaffold] 命令根据其架构生成类。这是需要与现有数据库协同工作的应用程序所采用的方法。生成的代码与我们手工编写的代码类似。

    namespace First;

// 商店的一篇文章：一个普通的 C# 类，与 EF Core 没有任何关联
public class Article
{
    // 主键（按约定：名为 Id 的属性）
    public int Id { get; set; }
    // 表的其他列
    public string Name { get; set; } = "";
    public decimal Price { get; set; }
    public int CurrentStock { get; set; }
    public int MinimumStock { get; set; }

    // 显示
    public override string ToString() => $"[{Id}, {Name}, {Price}, {CurrentStock}, {MinimumStock}]";
}
    • 第 4 行：一个普通的 C# 类。它不继承 EF Core 中的任何类，也没有任何特性；这称为 POCO （Plain Old CLR Object）；
    • 第 7 行：[Id] 属性将成为表的主键。这是 EF Core 的一项 约定 ：名为 [Id] （或 [ArticleId]，即类名后跟 [Id]）的属性就是主键。由于它是整数类型，其值将由 DBMS 生成（MySQL 的 [AUTO_INCREMENT] 列）；
    • 第 9–12 行：每个公共读/写属性都会成为同名的列。[Name] 属性用空字符串初始化，以满足编译器的要求（启用了可为 null 的类型：[string] 类型的属性不得保持为 [null]）；
    • 第 15 行：商品的便捷显示方式。

    {

    • 第 7 行：[DbContext] 类派生自 EF Core。[ArticlesContext] 对象表示与数据库的 工作会话 ：它在需要时打开连接，存储它读取的实体，并可以保存对这些实体的更改；
    • 第 10 行：[DbSet<Article>] 表示 articles 表。LINQ 查询在这里执行，商品也在这里添加或删除。该属性被定义为表达式主体成员，调用 [Set<Article>()]：上下文中声明的每个 [DbSet<T>] 都会将类型 [T] 引入模型；
    • 第 13 行：[OnConfiguring] 方法在首次使用上下文时由 EF Core 调用，用于配置上下文；
    • 第 15 行：连接字符串，与第 10 章中的相同：服务器、端口、数据库、用户名和密码（Laragon 用户 [root] 的密码为空）；

    • 第 20 行：[LogTo] 方法指示 EF Core 使用 [Console.WriteLine] 方法写入日志。我们只保留 [DbLoggerCategory.Database.Command] 消息类别（即已执行的 SQL 命令的类别），级别为 [LogLevel.Information]。如果没有这个过滤器，日志会非常冗长。查看发送到服务器的 SQL 是理解 EF Core 行为的最佳方式：我们将在所有示例中这样做。

    11.3. 模型

    EF Core 分三步根据实体构建其模型：

    • 首先，应用其 约定；
    • 然后使用应用于实体的 注解 （特性）对其进行补充或修正；
    • 最后，应用在上下文的 [OnModelCreating] 方法中用 C# 编写的配置：即流式 API。

    11.3.1. 约定

    我们在第一个示例中已经看到了其中的要点：

    • 任何带有 [get] 取值器和 [set] （或 [init]）赋值器的公共属性，都存储在同名的列中；
    • 属性 [Id] 或 [<Entity>Id] 是主键；如果它是整数，其值由 DBMS 生成；
    • 表名取自上下文的 [DbSet] 属性的名称（若没有，则取类的名称）；
    • 可为 null 类型（[int?]、[DateOnly?]、[string?]）的属性会生成 [NULL] 列；不可为 null 类型（[int]、[decimal]，以及启用可为 null 引用类型时的 [string] ）的属性会生成 [NOT NULL] 列；
    • 引用另一个实体的属性，或实体集合属性，定义了一种关系（稍后会介绍）。

    11.3.3. 可为 null 的类型与 NULL 列

    可为 null 的引用类型（C# 8，课程项目中通过 [<Nullable>enable</Nullable>] 启用）会影响模型：EF Core 会读取编译器生成的可为 null 性注解。[string] 属性 会生成 [NOT NULL] 列，而 [string?] 属性会生成 [NULL] 列。在未启用可为 null 类型的项目中，所有文本列都接受 [NULL]，除了标有 [Required] 的列。

    因此，必须谨慎地选择每个属性的类型：它既表达了 C# 代码规则（“该值可能缺失”），也表达了数据库约束。对于必填属性，有两种常见写法：

using Microsoft.EntityFrameworkCore;
using Microsoft.EntityFrameworkCore.Diagnostics;
using Microsoft.Extensions.Logging;

namespace Ef.Tools;

// EF Core 所执行 SQL 语句的紧凑日志
public static class SqlLog
{
    // DbContextOptionsBuilder 类型的扩展成员（C# 14）
    extension(DbContextOptionsBuilder options)
    {
        // options.WithSqlLog()：显示每条执行的 SQL 语句
        public DbContextOptionsBuilder WithSqlLog() => options.LogTo(Filter, Display);
    }

    // 选定的事件：SQL 命令执行成功或失败、事务的开始和结束
    private static bool Filter(EventId id, LogLevel level) =>
        id == RelationalEventId.CommandExecuted || id == RelationalEventId.CommandError
        || id == RelationalEventId.TransactionStarted
        || id == RelationalEventId.TransactionCommitted || id == RelationalEventId.TransactionRolledBack;

    // 显示一个事件
    private static void Display(EventData data)
    {
        switch (data)
        {
            case CommandExecutedEventData command:
                DisplayCommand(command.Command);
                break;
            case CommandErrorEventData error:
                DisplayCommand(error.Command);
                Console.WriteLine("    SQL> -- command failed");
                break;
            case TransactionEventData when data.EventId == RelationalEventId.TransactionStarted:
                Console.WriteLine("    SQL> -- start of transaction");
                break;
            case TransactionEventData when data.EventId == RelationalEventId.TransactionCommitted:
                Console.WriteLine("    SQL> -- transaction committed (COMMIT)");
                break;
            case TransactionEventData:
                Console.WriteLine("    SQL> -- transaction rolled back (ROLLBACK)");
                break;
        }
    }

    // 显示 SQL 语句（带缩进），然后显示其参数
    private static void DisplayCommand(DbCommand command)
    {
        // 忽略空行
        foreach (string line in command.CommandText.Split('\n').Select(l => l.TrimEnd()).Where(l => l != ""))
        {
            Console.WriteLine("    SQL> " + line);
        }
        if (command.Parameters.Count > 0)
        {
            var parameters = command.Parameters.Cast<DbParameter>()
                .Select(p => $"{(p.ParameterName.StartsWith('@') ? "" : "@")}{p.ParameterName}={p.Value}");
            Console.WriteLine($"    SQL> -- parameters: {string.Join(", ", parameters)}");
        }
    }
}

    11.5.2. 实体的状态

    变更跟踪基于每个实体的状态，状态是 [EntityState] 枚举中的一个值：

    状态
    含义
    [Detached]
    对象未被上下文跟踪（由 [new] 创建但尚未添加，或已从数据库中删除）
    [Added]
    对象已被添加到上下文（[Add]）：[SaveChanges] 会将其插入数据库
    [Unchanged]
    对象是从数据库读取的（或已保存），此后未被修改
    [Modified]
    至少有一个属性已被修改：[SaveChanges] 会发送 [UPDATE] 命令
    [Deleted]
    对象已被标记为删除（[Remove]）：[SaveChanges] 会发送 [DELETE] 命令

    请注意使用 EF Core 的工作周期：读取实体，像普通对象一样修改它们，添加和删除实体，然后调用 [SaveChanges]，它会将所有必要的命令以单个批次发送到数据库。上下文起着“工作单元”的作用。上下文是一个轻量级对象，生命周期很短：一个工作单元，例如 Web 应用程序中的一次 HTTP 请求。不会在应用程序的整个生命周期内使用同一个上下文，否则它会不断累积被跟踪的实体。

    11.6.2. IQueryable 与表达式树

    同一个 lambda 表达式，怎么既能在 C# 中对列表执行，又能在 [DbSet] 上被翻译为 SQL？第 7 章给出了答案：[DbSet<T>] 实现了 [IQueryable<T>] 接口，其方法 [Where]、[OrderBy]、[Select]……接收的不是委托（[Func<T, bool>]），而是 表达式树 （[Expression<Func<T, bool>>]）。编译器将 lambda 表达式 [a => a.CurrentStock < a.MinimumStock] 转换为描述它的数据结构（“参数 [a] 的属性 [CurrentStock] 与属性 [MinimumStock] 的比较 [<]”）；EF Core 遍历这个结构并生成等效的 SQL。像 [Rules.OutOfStock] 这样的方法在树中只表现为一次方法调用，其代码无法被分析：因此会出错。

    运算符是可组合的：查询可以分阶段构建，每个阶段都返回一个新的 [IQueryable<T>]，只有最后的执行（[ToList]、[First]、[Count]、[foreach]……）才会发送 SQL 命令：

    11.6.3. EF Core 9 与 C# 14 之间的不兼容

    在程序 [Linq] 中，列表 [names]被声明为 [List<string>] 类型而不是 [string[]]，并附有引用本段的注释。如果使用数组，查询 [context.Articles.Where(a => names.Contains(a.Name))] 可以编译，但在运行时会失败，抛出 [InvalidOperationException] 错误（“An exception was thrown while attempting to evaluate a LINQ query parameter expression”）。实际上，C# 14 将数组到 [ReadOnlySpan<T>] （第 5 章介绍的类型）的转换变成了隐式的语言转换，它也适用于调用扩展方法的对象。因此，对于数组，调用 [names.Contains(...)] 现在引用的是扩展方法 [MemoryExtensions.Contains(ReadOnlySpan<T>, T)] 而不是 [Enumerable.Contains(IEnumerable<T>, T)]：检查 lambda 表达式的表达式树就能明显看出这一点，而用 C# 13 编译的同一个程序（[<LangVersion>13</LangVersion>]）找到的是 [Enumerable.Contains] ，可以正常运行。EF Core 9 发布于 C# 14 之前，不认识这个方法：它试图对数组到 [ReadOnlySpan<string>] 的转换求值，以便将其作为 SQL 参数，结果失败（内部异常是由表达式树解释器抛出的 [ArgumentException]）。与 C# 14 同时发布的 EF Core 10 支持这种语法。使用 EF Core 9 时，可以像这里一样改用列表来绕过该问题，或者写成 [((IEnumerable<string>)names).Contains(a.Name)]。这是本章在 .NET 10 上使用 EF Core 9 时遇到的唯一问题。

    11.8. 迁移

    11.8.1. 原理

    到目前为止，数据库都是先由 [EnsureDeleted] 删除，再由 [EnsureCreated] 创建的。这对于线上运行的应用程序是行不通的：其数据库包含的数据在模型演进（新增一列、新增一张表）时必须保留。此外，[EnsureCreated] 只能创建不存在的数据库：如果数据库已经存在并带有表，它什么也不做，即使模型已经改变。

    迁移 正是为满足这一需求而设。迁移是一个 C# 类，由 [dotnet ef] 工具生成，它描述从模型的一个版本到下一个版本的过渡：其 [Up] 方法应用更改（创建表、添加列），而其 [Down] 方法则撤销更改。数据库中包含一张名为 [__EFMigrationsHistory] 的表，EF Core 在其中记录已应用于该数据库的迁移；这使它能够知道还有哪些迁移需要应用。

    11.10.1. 事务

    第 10 章介绍了事务：一组要么全部成功、要么全部失败的操作。使用 EF Core 时，有两个要点需要注意：

    11.10.2. 乐观并发

    两个用户读取同一个商品，其库存为 10。第一个用户卖出一件并将库存更新为 9。第二个用户在此次更新之前读取了库存，卖出三件并将库存更新为 7：第一个用户的销售丢失了。这就是丢失更新问题。

    一种解决方案是在每个用户操作的整个期间锁定该行（“悲观”并发）：这会阻塞其他用户，有时会阻塞很长时间。EF Core 实现的是乐观并发：不锁定任何内容，但在提交时，系统会验证该行自读取以来是否被修改过。为此，需要将一个或多个属性指定为并发令牌：EF Core 会在[WHERE]子句中为[UPDATE] 和[DELETE] 语句添加条件“令牌仍为读取时的值”。如果命令没有修改任何行，就意味着其他用户已经处理过这些行：EF Core 会抛出 [DbUpdateConcurrencyException]。

    11.12. 上下文与依赖注入

    前面的示例使用[new]创建上下文。在分层应用程序以及所有 ASP.NET Core 应用程序中，上下文由第 6 章介绍的依赖注入容器创建。为此，EF Core 提供了[IServiceCollection]的两个扩展方法：

    • [AddDbContext<T>(options => ...)] 以“[T]作用域”生存期注册上下文：容器为每个作用域创建一个上下文，将其提供给该作用域内所有请求它的服务，并在作用域结束时释放它。在 Web 应用程序中，每个 HTTP 请求都会创建一个作用域：每个请求都有自己的上下文，这对应于上下文的工作单元；
    • [AddDbContextFactory<T>(options => ...)] 注册上下文工厂，[IDbContextFactory<T>]，其方法[CreateDbContext] 在每次调用时创建一个新的上下文。它用于长时间运行的服务（单例），这类服务无法在应用程序的整个生命周期内保持同一个上下文；也用于并行处理，并行处理要求每个任务使用一个上下文。

    在这两种情况下，lambda 表达式都会接收一个 [DbContextOptionsBuilder] ，并像 [OnConfiguring] 那样配置上下文；上下文必须有一个接受 [DbContextOptions<T>] 的构造函数，就像 [ArticlesContext] 类中的那个。

    11.14. 结论：ADO.NET、Dapper 还是 EF Core？

    现在我们有两种访问数据库的方式：ADO.NET（第 10 章）和 EF Core（本章）。还有第三种被广泛使用的折中方式：Dapper，一个小型库（“微型 ORM”），它为 ADO.NET 连接添加了扩展方法。这些方法执行手写的 SQL 查询，并自动将结果中的行转换为对象：[connection.Query<Article>("SELECT * FROM articles WHERE Price > @price", new { price = 200 })]。SQL 由您编写，Dapper 负责将列映射到属性。

     
    优势
    劣势
    ADO.NET
    完全控制 SQL；性能好；无依赖项
    大量重复代码（参数、读取列）；SQL 写在字符串中，编译器不检查
    Dapper
    SQL 手写，但无需编写拷贝代码；性能与 ADO.NET 相近
    没有更改跟踪，也不生成[INSERT]/[UPDATE]；没有迁移
    EF Core
    LINQ 查询由编译器验证；更改跟踪；关系；迁移；独立于 DBMS
    多了需要理解的一层；需要监控生成的 SQL；不太适合复杂的批量处理

    可以提出以下指导原则：

    • EF Core 适用于大多数管理类应用程序：由相互关联的实体构成的模型、读取和更新实体的操作，以及随应用程序演进的架构。它是 ASP.NET Core 应用程序的默认选择；
    • ADO.NET或Dapper适用于希望精确控制所执行 SQL 的场合：复杂的报表查询、存储过程、处理海量数据，或者现有数据库的架构不适合面向对象模型；
    • 这些方法可以结合使用：应用程序可以在大部分场合使用 EF Core，而对少数关键查询使用手写 SQL 代码——借助[FromSql]、[SqlQuery]或 Dapper。EF Core 还提供对其所使用的 ADO.NET 连接的访问（[context.Database.GetDbConnection()]）。

    无论如何，了解 ORM 并不意味着不再需要理解 SQL 和 DBMS 的工作原理：本章中我们一直显示的已执行 SQL 命令日志，是验证 EF Core 实际行为的首要工具。
