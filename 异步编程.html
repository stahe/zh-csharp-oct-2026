    9. 异步编程

    上一章介绍了线程：我们可以“同时”执行多段代码，对它们进行同步，并把任务分配给线程池。本章在 2008 年的课程中并不存在，它讨论的是一个相关但不同的问题：如何编写这样一个程序，它要 等待 很长时间（等待磁盘、网络或数据库），却不在这些等待期间阻塞线程。.NET 中的答案在于 C# 语言的两个关键字 [async] 和 [await]，以及一个类型 [Task]。如今它们无处不在：后续各章将用它们来访问数据库（[OpenAsync]、[ExecuteReaderAsync]、[ToListAsync]、[SaveChangesAsync]），编写 TCP 服务器（[AcceptTcpClientAsync]）、Web 客户端（[HttpClient]）以及使用 ASP.NET Core 的 Web 服务。

    本章的所有示例都是单文件应用程序（[async-01.cs]、[async-02.cs]……），在 [09-async] 文件夹中使用 [dotnet run async-NN.cs] 运行。其中许多示例用秒表（[Stopwatch]）测量时长：显示的毫秒数在每次运行之间、在不同机器之间都会有所不同（这些示例是在一台双处理器机器上运行的）。重要的是 数量级：1 秒还是 3 秒，300 毫秒还是 0 毫秒。

    9.1. 为什么要异步

    9.1.1. 会等待的操作

    程序执行两类工作：

    • 计算任务，它们占用处理器：对列表排序、计算税款、分析文本；
    • 输入/输出 （I/O），本质上就是等待外围设备：从磁盘读取文件、向 Web 服务器发送请求并等待其响应、在数据库服务器上执行 SQL 查询。

    两者的数量级差别很大。处理器每秒执行几十亿条指令。对磁盘（SSD）的一次读取操作大约需要十分之一毫秒；在本地网络上的一次往返只需零点几毫秒；与位于全国另一端的服务器的一次往返需要几十毫秒；而一个稍复杂的 SQL 请求有时可能需要几秒钟。在这些等待期间，处理器本可以执行数百万条指令。

    当程序使用同步（阻塞）方法通过网络连接读取一行数据时，执行这次读取的线程会被 阻塞：它什么也不做，但仍然存在。它占用内存（它的栈，大约一兆字节），被操作系统所识别，而且最重要的是，它不能再用来做其他任何事情。在一次只做一件事的小型控制台程序中，这不成问题。但在两种情形下，问题就严重得多：

    • 在 服务器上：每个客户端由一个被阻塞的线程来服务，就会占用该线程。2008 年的课程在讨论异步 TCP 客户端的结论部分已经解释过这一点：如果线程池有 N 个线程，且这 N 个线程都在执行阻塞操作，那么就没有空闲线程可以服务新的客户端。现代 Web 服务器只用几十个线程就能处理成千上万个同时发生的请求：之所以能做到这一点，是因为它的线程从不在 I/O 上被阻塞；
    • 在 图形用户界面中：单个线程（UI 线程）负责处理点击并重绘窗口。如果它被一次下载阻塞，窗口就会冻结。

    异步 就是启动 I/O 操作，在其运行期间 释放 线程（硬件和操作系统传输数据时并不需要它），然后在操作完成后恢复工作，可能是在另一个线程上：

    • 在 [1] 中，线程 T1 启动 I/O，并一直阻塞到它完成；
    • 在 [2] 中，线程 T1 启动 I/O 后返回线程池，在那里它可以处理其他请求。当 I/O 操作完成时，系统通知 .NET，由 .NET 让线程池中的一个线程（T2，或者在 T1 空闲时由 T1）执行处理的 其余部分。

    [async-01.cs] 程序在 100 次操作上测量这一差异，每次操作都等待一秒（用等待来模拟 I/O）。它使用了我们将在本章后面解释的指令（[Task.Run]、[Task.Delay]、[await]）；这里我们只关心结果。

    // 为什么要异步：100 个操作，每个都要等待一秒
// （等待模拟一次 I/O：磁盘读取、网络请求、SQL 查询……）
using System.Diagnostics;

const int nbOperations = 100;
Console.WriteLine($"{nbOperations} operations of one second, {Environment.ProcessorCount} processors");

// 1 - 每个操作一个线程，每个线程在等待期间被阻塞
var stopwatch = Stopwatch.StartNew();
var threads = new Thread[nbOperations];
for (int i = 0; i < nbOperations; i++)
{
    threads[i] = new Thread(() => Thread.Sleep(1000));
    threads[i].Start();
}
Display("1 - one thread per operation", ProcessThreads());
foreach (var thread in threads)
{
    thread.Join();
}
Display("    end");

// 2 - 把操作交给线程池，但它们会阻塞线程池
stopwatch.Restart();
var tasks = new Task[nbOperations];
for (int i = 0; i < nbOperations; i++)
{
    tasks[i] = Task.Run(() => Thread.Sleep(1000));
}
Display("2 - thread pool, blocking waits", ProcessThreads());
Task.WaitAll(tasks);
Display("    end");

// 3 - 异步等待：等待期间不阻塞任何线程
stopwatch.Restart();
for (int i = 0; i < nbOperations; i++)
{
    tasks[i] = Task.Delay(1000);
}
Display("3 - asynchronous waits", ProcessThreads());
await Task.WhenAll(tasks);
Display("    end");

// 启动各操作半秒后，进程的线程数
int ProcessThreads()
{
    if (stopwatch.ElapsedMilliseconds < 500)
    {
        Thread.Sleep(500 - (int)stopwatch.ElapsedMilliseconds);
    }
    using var process = Process.GetCurrentProcess();
    return process.Threads.Count;
}

// 显示耗时，以及（如果提供）线程数
void Display(string message, int? nbThreads = null)
{
    string threadsInfo = nbThreads is null ? "" : $", {nbThreads,3} threads in the process";
    Console.WriteLine($"{message,-42} : {stopwatch.ElapsedMilliseconds,5} ms{threadsInfo}");
}

    • 第 23–31 行：这些操作被委托给线程池（[Task.Run]），线程池已在上一章介绍过。线程池起初拥有与处理器数量相同的线程（此处为 2 个），只有在它们全部忙碌时才会逐步增加，因为它假定自己的线程在进行计算，没有必要让线程数量远远超过处理器数量。但在这里，它的线程并没有在计算：它们处于空闲状态。这些操作要等待空闲线程，整个过程耗时……超过二十秒（第 6 行）。这就是所谓的“线程池饥饿”，是将线程池与阻塞式 I/O 结合使用的服务器中最常见的缺陷；
    • 第 34–41 行：这些等待是异步的（用 [Task.Delay] 代替 [Thread.Sleep]）。等待期间没有线程被阻塞：系统定时器会在一秒后唤醒 .NET。整个过程持续一秒，线程数量不会增加（第 7 行显示的线程是线程池在第 2 步期间创建的；它们处于空闲状态）；
    • 第 51 行：[Process.GetCurrentProcess()] 提供对当前正在运行的进程的访问；其属性 [Threads] 是它的线程集合（包括 .NET 的线程和系统的线程）。

    让我们记住这个教训：等待时不能阻塞线程。异步并不会让 I/O 更快；它让你可以用很少的线程同时处理许多 I/O 操作，并让应用程序所需的线程保持可用（GUI 线程、服务器线程池中的线程）。

    9.1.2. 三种先后出现的模型

    .NET 提出了三种编写异步代码的方式。前两种仍会出现在遗留代码和较早的文章中，因此认识它们是有用的。

    模型
    起源
    原理
    APM（“异步编程模型”，Asynchronous Programming Model）
    .NET 1.0（2002）
    一对方法：[BeginXxx] 和 [EndXxx]。[BeginXxx] 启动操作并接收一个回调方法（[AsyncCallback]）；该回调方法在操作结束时由线程池中的线程执行，并调用 [EndXxx] 来获取结果或异常。示例：[Socket.BeginConnect] / [EndConnect]，2008 年课程中的异步 TCP 客户端就使用了它们。
    EAP（“基于事件的异步模式”，Event-based Asynchronous Pattern）
    .NET 2.0（2005）
    一个启动操作的 [XxxAsync] 方法和一个在操作完成时触发的 [XxxCompleted] 事件。示例：[WebClient.DownloadStringAsync] 和 [DownloadStringCompleted]，以及 2008 年课程中学习过的 [BackgroundWorker] 类（事件 [DoWork]、[ProgressChanged]、[RunWorkerCompleted]）。
    TAP（“基于任务的异步模式”，Task-based Asynchronous Pattern）
    .NET 4.0（2010），C# 5（2012）
    一个返回任务（[XxxAsync] [Task] 或 [Task<T>]）的方法，该任务代表当前的操作。调用方代码使用关键字 [await] 等待该任务。这是当前的模型，也是本课程其余部分唯一使用的模型。

    APM 和 EAP 模式有同样的缺陷：代码被拆成了若干片段。本来自然读作“先连接，再读取，然后显示”的逻辑，变成了一个启动连接的方法、一个开始读取的回调方法，以及另一个显示数据的回调方法；变量必须在这些方法之间共享，异常在不同的地方处理，而一个简单的循环（“只要还有数据就读取”）则变成一个递归调用自身的回调方法，就像 2008 年课程中的读取方法（[lecture]）那样。TAP 模式配合 [async] 和 [await]，使你可以编写 形式上与同步代码一样的异步代码。

    程序 [async-02.cs] 按照 APM 和 TAP 这两种极端模型编写了同一个 TCP 客户端。它还包含一个由线程运行的小型服务器，可响应两个客户端（网络编程将在第 12 章详细介绍；目前只需知道，客户端连接到服务器并读取服务器发送给它的消息即可）。

    // 同一个 TCP 客户端，先用 2008 年的 APM 模型编写，再用当前的 TAP 模型编写
using System.Net;
using System.Net.Sockets;
using System.Text;

const int port = 27500;
// 一个最小化的服务器，由一个线程执行：它为两个客户端服务后停止
var listener = new TcpListener(IPAddress.Loopback, port);
listener.Start();
var server = new Thread(() =>
{
    for (int i = 1; i <= 2; i++)
    {
        using Socket service = listener.AcceptSocket();
        // 服务器需要一些时间才回答
        Thread.Sleep(500);
        service.Send(Encoding.UTF8.GetBytes($"Hello client no. {i}"));
    }
    listener.Stop();
});
server.Start();
Display("start of the program");

// 1 - APM 模型（Asynchronous Programming Model，异步编程模型）：BeginXxx / EndXxx 和回调方法
var end = new ManualResetEventSlim(false);
byte[] buffer = new byte[1024];
var client = new Socket(AddressFamily.InterNetwork, SocketType.Stream, ProtocolType.Tcp);
// 我们发起连接，并给出完成时要回调的方法
client.BeginConnect(IPAddress.Loopback, port, Connected, client);
Display("APM: connection launched, the program goes on");
// 主线程已无事可做：它等待最后一个回调方法的信号
end.Wait();

// 回调方法 1：连接已建立
void Connected(IAsyncResult result)
{
    // 我们取回作为 BeginConnect 最后一个参数传入的对象
    var socket = (Socket)result.AsyncState!;
    // 我们结束该操作（如果失败，抛出异常的是 EndConnect）
    socket.EndConnect(result);
    Display("APM: connected, read launched");
    // 我们发起对服务器回答的读取，使用另一个回调方法
    socket.BeginReceive(buffer, 0, buffer.Length, SocketFlags.None, Received, socket);
}

// 回调方法 2：数据已到达
void Received(IAsyncResult result)
{
    var socket = (Socket)result.AsyncState!;
    int nbBytes = socket.EndReceive(result);
    Display($"APM: received [{Encoding.UTF8.GetString(buffer, 0, nbBytes)}]");
    socket.Close();
    // 我们通知主线程
    end.Set();
}

// 2 - TAP 模型（Task-based Asynchronous Pattern，基于任务的异步模式）：XxxAsync 和 await
using (var client2 = new Socket(AddressFamily.InterNetwork, SocketType.Stream, ProtocolType.Tcp))
{
    await client2.ConnectAsync(IPAddress.Loopback, port);
    Display("TAP: connected, read launched");
    int nbBytes = await client2.ReceiveAsync(buffer);
    Display($"TAP: received [{Encoding.UTF8.GetString(buffer, 0, nbBytes)}]");
}
server.Join();

// 显示内容以执行它的线程编号为前缀
static void Display(string message)
{
    Console.WriteLine($"[thread {Environment.CurrentManagedThreadId,2}] {message}");
}

      • 第 32 行：主线程已无事可做。为防止程序在交换完成之前终止，它等待最后一个回调方法发出的信号：一个 [ManualResetEventSlim] 对象，其 [Wait] 方法会阻塞调用它的线程，直到另一个线程调用其 [Set] 方法（这是线程部分所见 [AutoResetEvent] 屏障的轻量级版本）；
      • 第 35–43 行：连接回调方法。它必须用收到的参数调用 [EndConnect] ：这个调用终止该操作，如果连接失败还会抛出异常。然后它用 [BeginReceive] 启动读取操作，并指定第二个回调方法 [Received]；
      • 第 47–54 行：读取回调方法用 [EndReceive] 获取收到的字节数，显示消息，关闭套接字，并释放主线程；
      • 结果表明，回调方法是由主线程以外的线程执行的（是线程池中的线程，而不是线程 1）；
    • 第 57–65 行：使用 TAP 模型的同一个客户端。[ConnectAsync] 和 [ReceiveAsync] 返回任务，而 [await] 等待它们完成，且不阻塞线程：代码像同步代码一样自上而下阅读；变量是普通的局部变量；没有回调方法或信号需要管理。执行其余代码的线程通常不再是线程 1：我们将在“由哪个线程执行其余部分？”一节解释原因；
    • 第 68 行：每条显示的内容都以执行它的线程的编号作为前缀，该编号来自 [Environment.CurrentManagedThreadId]。

    没有必要记住 APM 模式。如果你需要使用只提供这种模式的旧库，方法 [Task.Factory.FromAsync] 可以把一对 [BeginXxx] / [EndXxx] 转换成返回 [Task] 的方法；在关于 [TaskCompletionSource] 的一节中，我们将看到如何把基于事件的 API（EAP 模型）转换成任务。

    9.2. 任务：Task 与 Task<T>

    任务 是表示正在进行或已完成的操作的对象：

    • [Task] 表示不返回结果的操作；
    • [Task<T>] 表示将返回类型为 [T] 的结果的操作。[Task<T>] 派生自 [Task]。

    任务不是线程。任务可以由线程池中的线程执行（由 [Task.Run] 创建的任务就是这种情况），但许多任务并不由任何线程执行：[Task.Delay(1000)] 返回的任务只是在一秒后由定时器“完成”；[ReceiveAsync] 返回的任务在系统发出数据已到达的信号时完成。任务是对结果的一个 承诺 ，可以对它进行查询（它完成了吗？成功了吗？）和等待。

    • 第 31–36 行：函数抛出异常的任务以状态 [Faulted] 结束。异常保留在任务内部，而 [await] 会重新抛出它；可以用标准的 [try / catch] 捕获它；

    // 编译器生成的内容（大幅简化）
Task<int> CountSugarsAsync(int count)
{
    var machine = new CountSugarsMachine { count = count, state = 0 };
    machine.Advance();         // 执行方法直到第一个 await
    return machine.ResultTask; // 状态机稍后会完成的任务

class CountSugarsMachine
{
    public int count, i, state;               // 局部变量变成字段
    public TaskCompletionSource<int> Source = new();
    public Task<int> ResultTask => Source.Task;

    public void Advance()
    {
        if (state == 0) { i = 1; }             // 第一次进入：循环开始
        else { Console.WriteLine($"  sugar no. {i}"); i++; }   // await 之后恢复执行
        if (i <= count)
        {
            state = 1;
            // 我们请求在延迟结束时被回调，然后交还控制权
            Task.Delay(200).GetAwaiter().OnCompleted(Advance);
            return;
        }
        Source.SetResult(count);               // 方法结束：任务完成
    }
}

    这与 APM 模型中回调方法的原理相同（[OnCompleted(Advance)] 请求在操作结束时进行回调），但拆分方法、保存变量和处理异常的是编译器。而开发者编写的是一个自上而下阅读的方法。你可以使用 ILSpy 之类的反编译器，或在 SharpLab 网站上查看实际生成的代码；它要长得多，特别是因为它还要处理所等待的任务已经完成的情形（此时执行会不间断地继续）以及异常的情形。

    9.6. 取消与超时

    9.6.1. CancellationTokenSource 与 CancellationToken

    长时间运行的异步操作必须是 可取消的：用户点击了 [Cancel]，Web 服务器客户端断开了连接，应用程序关闭了，或者超时了。为此，.NET 使用一种 协作式 机制，涉及两个对象：

    • 一个 [CancellationTokenSource] （取消源），由决定取消的代码持有。它的 [Cancel()] 方法请求取消；[CancelAfter(delay)] 在超时后自动请求取消；
    • 一个 [CancellationToken] （取消令牌），通过源的 [Token] 属性获得，并作为参数传给可取消的操作。操作检查该令牌（[IsCancellationRequested]），或者在已请求取消时要求它抛出异常（[ThrowIfCancellationRequested()]），并把它传递给自己所调用的操作。

    这一机制是协作式的：没有人会强行中断某个操作（2008 年课程中的 [Thread.Abort] 方法在当前的 .NET 中已经过时：它只会抛出 [PlatformNotSupportedException]）；操作会在能够干净地停止的某个点自行停止。按照约定，被取消的操作以抛出 [OperationCanceledException] 结束，其任务的状态为 [Canceled]。

    public int NbCacheAccesses { get; private set; }

    public ValueTask<decimal> ReadRateAsync(string code)
    {

        {
            // 快速的同步路径：结果已经已知
            NbCacheAccesses++;
            return ValueTask.FromResult(rate);

            "USD" => 1.17m,
            "GBP" => 0.87m,
            _ => throw new ArgumentException($"unknown currency: {code}"),
        };
        cache[code] = rate;
        return rate;
    }

    9.10.2. ConfigureAwait 与同步上下文

    程序 [async-05.cs] 已经表明，在控制台中，方法在 [await] 之后的剩余部分由池中的任意线程执行。在图形应用程序（Windows Forms、WPF、MAUI）中并非如此。图形组件只能由 UI 线程操作：2008 年的课程不得不在其回调方法中使用 [listBoxEvts.Invoke(...)]，以便让该线程执行更新。有了 [await]，这就不再必要了：界面线程拥有一个同步上下文 （[SynchronizationContext.Current] 不为 [null]），由 [await] 保存；等待结束时，方法的其余部分会交还给该上下文，从而由界面线程执行。我们可以这样写：

    • 在应用程序代码（图形用户界面、控制台程序、ASP.NET Core 应用程序）中，则不要写它。控制台程序和 ASP.NET Core 应用程序本来就没有同步上下文：[ConfigureAwait(false)] 在那里没有任何区别。

// 把温度计的 MeasureTaken 事件转换为任务
static Task<double> WaitForTemperatureAsync(Thermometer thermometer, double threshold, CancellationToken token)
{
    // 任务的源，由我们自己来完成它
    var source = new TaskCompletionSource<double>(TaskCreationOptions.RunContinuationsAsynchronously);
    // 用取消令牌注册的回调，任务完成时要释放
    CancellationTokenRegistration registration = default;
    // 事件处理程序在达到阈值时完成任务
    void OnMeasure(object? sender, double temperature)
    {
        if (temperature >= threshold && source.TrySetResult(temperature))
        {
            thermometer.MeasureTaken -= OnMeasure;
            registration.Dispose();
        }
    }
    thermometer.MeasureTaken += OnMeasure;
    // 取消请求使任务以 Canceled 状态完成
    registration = token.Register(() =>
    {
        if (source.TrySetCanceled(token))
        {
            thermometer.MeasureTaken -= OnMeasure;
        }
    });
    // 任务立即返回；它稍后才会完成
    return source.Task;
}

    9.11.2. 生产者/消费者：System.Threading.Channels

    上一章使用 生产者/消费者模式介绍了 [BlockingCollection<T>] 集合：生产者线程将元素加入队列，消费者线程将其取出；只要队列为空，[Take] （或枚举 [GetConsumingEnumerable]）就会阻塞消费者；只要有界队列已满，[Add] 就会阻塞生产者。这些等待都会阻塞线程。通道（Channel）位于 [System.Threading.Channels] 命名空间（.NET Core 3.0）中，以异步等待的方式提供同样的功能：

    • [Channel.CreateBounded<T>(capacity)] 创建有界通道，[Channel.CreateUnbounded<T>()] 创建无界通道；
    • [Writer] 属性（[ChannelWriter<T>]）供生产者使用：[WriteAsync] 发布一个项（异步等待出现可用空间），[TryWrite] 尝试立即添加它，[Complete] 表示不会再有更多元素；
    • [Reader] 属性（[ChannelReader<T>]）供消费者使用：[ReadAsync] 获取一个元素，而 [ReadAllAsync] 返回包含所有元素的异步流，当通道被 [Complete] 关闭且为空时，该流结束。

using System.Diagnostics;
using System.Threading.Channels;

var stopwatch = Stopwatch.StartNew();
// 有界通道：最多包含 2 个等待处理的订单
Channel<int> channel = Channel.CreateBounded<int>(2);

Task producer = ProduceAsync(channel.Writer, 8);

// 生产者：每 50 毫秒一个订单
async Task ProduceAsync(ChannelWriter<int> writer, int nbOrders)
{
    for (int i = 1; i <= nbOrders; i++)
    {
        await Task.Delay(50);
        // 如果通道中有空位，TryWrite 会立即写入订单，否则立即丢弃
        if (writer.TryWrite(i))
        {
            Display($"P  : order {i} dropped");
        }
        else
        {
            // 通道已满：WriteAsync 等待（不阻塞线程）直到有空位被释放
            Display($"P  : channel full, order {i} waits");
            await writer.WriteAsync(i);
            Display($"P  : order {i} dropped");
        }
    }
    // 不会再写入任何内容：消费者将退出它们的循环
    writer.Complete();
    Display("P  : end of the production");
}

// 一个消费者：处理一个订单需要 400 毫秒
async Task ConsumeAsync(string name, ChannelReader<int> reader)
{
    // ReadAllAsync 返回一个异步流，在通道关闭且为空时结束
    await foreach (int order in reader.ReadAllAsync())
    {
        Display($"{name} : processing of order {order}");
        await Task.Delay(400);
    }
    Display($"{name} : no more orders");
}

void Display(string message)
{
    Console.WriteLine($"{stopwatch.ElapsedMilliseconds,5} ms : {message}");
}

    9.12. 时间：PeriodicTimer 与 TimeProvider

    两个较新的类完善了与时间相关的工具：

    • [PeriodicTimer] （.NET 6）是一个与 [await] 配合使用的计时器：其方法 [WaitForNextTickAsync] 返回一个在下一次“滴答”时完成的任务。与 [System.Threading.Timer] （用于 [async-19.cs]）不同，后者会在池中的线程上调用回调方法——可能在上一次调用仍在进行时——[PeriodicTimer] 被写成一个简单的循环，并且永远不会让两次执行重叠；
    • [TimeProvider] （.NET 8）是一个抽象类，表示时钟：当前时间（[GetUtcNow]、[GetLocalNow]）、计时（[GetTimestamp]、[GetElapsedTime]）以及计时器的创建。[TimeProvider.System] 是系统时钟。依赖时间的类接收一个 [TimeProvider] ，而不是直接使用 [DateTime.Now]：这样就可以用受控的时钟对其进行测试。

// 读取税率档次（limit:coeffR:coeffN，小数点）
static async Task<TaxBracket[]> LoadBracketsAsync(string file, CancellationToken token)
{
    string[] lines = await File.ReadAllLinesAsync(file, token);
    return [.. lines.Where(l => l.Trim() != "").Select(TaxBracket.Parse)];
}

// 读取纳税人（已婚 子女数 工资），计算他们的税额并写入结果
static async Task<int> CalculateTaxesAsync(TaxBracket[] brackets, string input, string output, CancellationToken token)
{
    int nbLines = 0;
    await using var writer = new StreamWriter(output);
    await foreach (string line in File.ReadLinesAsync(input, token))
    {
        string[] fields = line.Split(' ', StringSplitOptions.RemoveEmptyEntries);
        string result = fields switch
        {
            [var m, var c, var s] when m is "y" or "n" && int.TryParse(c, out int children) && children >= 0
                                       && int.TryParse(s, out int salary) && salary >= 0
                => $"tax = {CalculateTax(brackets, m == "y", children, salary)} €",
            _ => "incorrect line",
        };
        await writer.WriteLineAsync($"{line,-12} : {result}");
        nbLines++;
    }
    return nbLines;
}

// 税额计算（2004 年税率表，应用于 2003 年收入，为练习保留）
static int CalculateTax(TaxBracket[] brackets, bool married, int nbChildren, int salary)
{
    decimal shares = married ? nbChildren / 2m + 2 : nbChildren / 2m + 1;
    if (nbChildren >= 3)
    {
        shares += 0.5m;
    }
    decimal income = 0.72m * salary;
    decimal quotient = income / shares;
    // 限额超过家庭系数的第一个档次，否则取最后一个档次
    TaxBracket bracket = brackets.FirstOrDefault(t => quotient <= t.Limit, brackets[^1]);
    return (int)(bracket.CoeffR * income - bracket.CoeffN * shares);
}

    {
        string[] fields = line.Split(':');
        return new TaxBracket(decimal.Parse(fields[0], CultureInfo.InvariantCulture),
                                decimal.Parse(fields[1], CultureInfo.InvariantCulture),
                                decimal.Parse(fields[2], CultureInfo.InvariantCulture));
    }
}

    9.14. 黄金法则

    让我们总结一下 .NET 异步编程的规则：

    • 一路 async 到底：等待异步操作的方法本身也要变成异步方法（[async Task]），其调用方也是如此，一直追溯到入口点（异步的 [Main] 、事件处理程序、ASP.NET Core 控制器操作）。将异步代码与阻塞等待混用会抵消异步的好处；
    • 不要对未完成的任务使用 [.Result]、[.Wait()] 或 [Task.WaitAll] ：请改用 [await]、[Task.WhenAll]、[Task.WhenAny] 或 [Task.WhenEach]。这些阻塞形式会冻结线程，并可能在图形应用程序中造成永久死锁；
    • 不要在异步代码中使用 [Thread.Sleep] ：而应使用 [await Task.Delay(...)]；
    • 不要编写 [async void] 方法，GUI 事件处理程序除外；异步方法应使用 [Task] 或 [Task<T>] （在特殊情况下可使用 [ValueTask<T>]）；
    • 异步方法的名称以 [Async] 结尾：[CalculateTaxesAsync]、[ReadRateAsync]；
    • 可取消的异步方法接收一个 [CancellationToken] 作为其最后一个参数，并将它传递给它调用的所有异步操作；被取消的操作以 [OperationCanceledException] 结束；
    • [Task.Run] 专用于你希望在后台执行的计算（例如，避免阻塞 GUI 线程）。不要为了“使其异步”而把同步 I/O 操作包装在 [Task.Run] 中：请使用该操作的 [XxxAsync] 版本；
    • 先启动，后等待：要同时运行多个相互独立的操作，请先将它们全部启动，然后使用 [Task.WhenAll] 等待它们；要限制操作的数量，请使用 [Parallel.ForEachAsync] 或通道；
    • [ConfigureAwait(false)] 用于库中，而不用于应用程序中；
    • 已启动的任务必须被等待（或使用 [_ =] 显式忽略，同时处理其异常）：被遗忘的任务会隐藏其异常，并可能因程序结束而被中断。
